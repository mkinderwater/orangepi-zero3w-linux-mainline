# M2x hardware and build experiments: retained outcomes and options

**Evidence cutoff:** November 15, 2026. This record reconciles the M2c* / M2d* trial results already published in [the detailed investigation](../ORANGE_PI_ZERO_3W_LINUX_6_18_BOOT_INVESTIGATION_2026-11-15.md), [the boot-handoff history](boot-handoff-and-failures.md), and [the vendor M2 control test](hardware-test-2026-11-14.md), then places them alongside the later A2/VBI/F1 results. **No new M2x hardware test was conducted for this update.**

## What M2x actually established

The M2c/M2d series made progress isolating **image assembly and U-Boot execution**, but it never supplied positive evidence of **our Linux 6.18.19 kernel running** on the Orange Pi Zero 3W. Later F1 demonstrated that even a fully booted vendor kernel can leave the HDMI bootloader splash on screen, so that symptom is not a kernel-entry measurement.

### U-Boot: the specific overlap discovered

Original 2018 vendor U-Boot boot-script load/execution address: `0x43100000`. The earlier M2 experimental raw kernel loaded at `0x41000000` and had a 41,064,960 byte file footprint to `0x43729A00`; its declared header footprint ended around `0x437F0000`. **Both include `0x43100000`**. Merely setting a different `load_addr` *inside a script executing at that address* does not move the executing script.

M2cv relocated its second-stage script to `0x46000000`, DTB to `0x44000000`, initramfs to `0x45000000`. The vendor M2cv CONTROL physically booted. This confirms the relocation strategy can preserve a vendor boot path, not that every experimental handoff is correct.

Later 0.2.7 HBI Image is far smaller (8,591,368 byte file; 9,043,968 byte declared), and the [finished-image audit](2026-11-15-boot-chain.md) found no static kernel/script/DTB/initrd overlap. Do **not** misapply the older 41 MiB collision diagnosis to HBI-027.

### Deterministic diagnostic defects

- Early M2cr initramfs called `busybox blkid`, but the installed binary lacked that applet; it had `findfs`. Corrected root UUID lookup to `busybox findfs UUID=...`. This was a real diagnostic-code defect, not proof of where Linux stopped.
- A CPIO extraction validator initially searched `./init` instead of `init`; a test false positive, not hardware evidence.
- The M2ct tests differed in ramdisk format/handoff. Their failure does not prove either format is invalid universally.
- FAT `.MRK` templates that say `REACHED` are not evidence of execution. Actual `.LOG` markers are the ones written at runtime.

## Bridge from M2x to later verified hardware results

| Later test | Why it matters to M2x |
| --- | --- |
| A2P/A2V | Vendor boot works if original boot-script semantics are preserved, including nested second stage |
| S1/S2 | Removing vendor FDT preparation or environment import breaks those tested boot paths |

## M2x experiment options for next work

1. **No rerun of fixed M2x packaging failures.** Preserve source and pinned build outputs; the two-stage loader, Boot0 and vendor `booti` have later hardware controls.
2. **Separate kernel entry from display.** Do not diagnose failure from frozen HDMI or LED alone. Prove physical UART pinmux on the vendor kernel first, or use a validated non-destructive early GPIO signal.
3. **Keep two independent experiments per batch.** One boot-handoff diagnostic, one kernel-entry/early initialization diagnostic, each with one intentional changed variable.
4. **Validate exact load ranges and FDT reservations.** Earlier huge raw Image had a real script collision; smaller hybrid Image did not. Account for initramfs relocation and `bl31` at `0x48000000`.
5. **Reconstruct the actual 0.2.7 BSP import.** Compare imported `bsp/` against pinned Allwinner BSP and capture `Kbuild`/`Kconfig` changes with [source audit script](../scripts/audit-hybrid-027-source.py).
6. **Prioritize a hardware-proven 6.6.98 control.** The newly rebuilt `control` and `identity` outputs are offline PASS only; test their independent HDMI, Wi-Fi and MMC behavior before reintroducing 6.18.

## Do not repeat these assumptions

- A 6.18 kernel is running merely because U-Boot reached `booti`.
- A frozen screen means the CPU stopped in U-Boot. F1 disproves that inference.
- A red LED being solid, blinking or going off isolates the failure without a verified LED trigger.
- Removing `vmmc-supply` is a safe generic PMIC fix.
- `blkid` exists in any BusyBox binary.
- Changing `&osc` to 24 MHz or UART pins to PB9/PB10 was separately validated in M2cx.
- The vendor 6.6 DTS's static 512 MiB node should be hardcoded to the tested 1 GiB. F1 runtime U-Boot adjusted it.
