# A733 IOMMU v20 cross-check, before integrating Linux 6.18

**Date:** 2026-11-18. **Status:** vendor/upstream source inspected; local 6.18 API and DT detail audit pending. **No driver code, kernel config or DTB modified.**

## Direct source findings

1. The pinned [Allwinner BSP IOMMU v2 source](https://github.com/alexcaoys/allwinner-bsp/blob/656a550c826787e7e72fae58ca793df9e0988ac8/drivers/iommu/sunxi-iommu-v2.c) is approximately 1,820 lines. Its platform match table at ~1790 uses `allwinner,iommu-v20`. It registers its own IOMMU ops via `iommu_device_register()`, has `sunxi_iommu_domain_alloc_paging`, `sunxi_iommu_of_xlate` and explicit page table and MIC hardware controls.
2. [Vendor Kconfig](https://github.com/alexcaoys/allwinner-bsp/blob/656a550c826787e7e72fae58ca793df9e0988ac8/drivers/iommu/Kconfig) defines `AW_IOMMU` and `AW_IOMMU_V2`; the driver is composed from `sunxi-iommu-common.c`, `sunxi-iommu-pgtable.c` and `sunxi-iommu-v2.c`, plus headers. **Porting a single .c file cannot provide the full implementation.**
3. In upstream [Linux sun50i-iommu.c at the accepted A733 clock commit](https://github.com/torvalds/linux/blob/308e4087bbda07814fe06e5ee9450ace0d89e15c/drivers/iommu/sun50i-iommu.c#L1073-L1086), the OF match table contains `allwinner,sun50i-h6-iommu` and `allwinner,sun50i-h616-iommu`, **not** `allwinner,iommu-v20`. Therefore that upstream driver is **NOT_APPLICABLE as a drop-in A733 v20 driver**; hardware register/IP equivalence and IOMMU DMA mapping would need proof.
4. Our compiled stage4 6.18 kernel has `CONFIG_IOMMU_SUPPORT=n`, while the full vendor DTB describes `iommu@3900000` with `allwinner,iommu-v20`, two IRQs, per-master `iommus` specifiers and explicit clocks. The vendor DE node has an IOMMU relationship; the exact provider and stream values must be extracted from the existing DTS audit, not guessed.
5. The [Jonas5 A733 6.18 tree](https://github.com/jonas5/Allwinner-A733-kernel) documents the display/GPU stack but its GitHub tree does **not** expose a directly matching `drivers/iommu/sunxi-iommu-v2.c` source in the visible project files; its documentation explicitly separates some vendor/proprietary modules from Git. This absence does **not** establish that the project lacks hardware IOMMU functionality.
6. Existing Allwinner/H616 IOMMU, the 2026 A733 CCU bus-gate patches, and A733 upstream platform submissions are **relevant supporting code**, but are not direct v20 implementation patches. In initial focused web searches, no reviewed/merged A733 v20 IOMMU driver patch was verified. This is **search-limited**, not a claim that none exists.

## Required checks before implementation

- Inspect the **actual** 6.6.98 vendor source from `/root/opi3w-vendor-6698-work/kernel/bsp/drivers/iommu/`, including build support Kconfig/Makefile.
- Compare against exact custom 6.18 tree at `/root/opi3w-m2-work/linux-618-hdmi-stage4/linux`; verify all IOMMU framework method signatures, DMA attach/map/unmap, domain handling and internal-header use.
- Decode IOMMU provider and display DMA consumer nodes from existing full vendor DTS, including register size, two IRQs, clock/reset IDs, `#iommu-cells`, DE stream IDs and IOMMU group relationships. Do not duplicate phandle audit already completed.
- Cross-check target APIs against latest accepted upstream implementation and search open GitHub issues/PRs and mailing-list patches before committing a port. An older vendor source may be incomplete.
- Stage changes on a **separate** kernel source and output tree. Keep `CONFIG_IOMMU_SUPPORT=n` in the validated control kernel and DTB.
- Require source compile, read-only IOMMU provider probe, map/unmap tests, and actual display DMA validation before enabling the DE352 consumer. Do not touch boot firmware.

## New audit script

`scripts/crosscheck-a733-iommu-v20.py` verifies source inputs, hashes relevant files, lists required IOMMU API usage and exact Linux 6.18 header occurrences, audits config, and extracts vendor DTS provider/consumer references. Run on Debian:

```sh
python3 scripts/crosscheck-a733-iommu-v20.py
```

Output: `/root/opi3w-m2-work/linux-618-hdmi-stage4/artifacts/iommu-v20-source-crosscheck/summary.md`.

**Caveat:** name matching alone is not an ABI validation. Each method signature and expected return type needs explicit review after host-generated report. If local BSP paths differ, stop and locate the real source; do not substitute unrelated files.

**Decision:** **HOLD** IOMMU v20 integration until API, clock, reset, DMA and provider differences have been reviewed. Do not blindly enable `CONFIG_SUN50I_IOMMU` or add the A733 compatible to the H6 driver.

## Exact Linux 6.18 domain API follow-up: operator host report, November 18

The operator ran the targeted read-only `iommu-v20-domain-review.txt` extraction against the **local** vendor BSP and patched Linux 6.18 checkout. This report is more authoritative for the target than generic upstream API assumptions. No kernel source or images were changed.

### Active vendor preprocessor paths

- `sunxi-iommu-v2.c` defines `SEPERATE_DOMAIN_API` at line 314 and `COOKIE_HANDLE_BY_CORE` at line 323; `sunxi-iommu.h` also defines these macros and `DETACH_OP_DEPRECATED`.
- Therefore explicit `iommu_get_dma_cookie()` and `iommu_put_dma_cookie()` calls in `#ifndef COOKIE_HANDLE_BY_CORE` are inactive in the captured vendor source configuration. Both functions actually exist under Linux 6.18 `drivers/iommu/dma-iommu.h` / `dma-iommu.c`; **absence from `include/linux/iommu.h` did not mean removal**.
- Verify the exact `#if` region of both `iommu_ops` definitions and their compiled configuration before porting; the prior name-only scan captured both conditional branches.

### Source-proven adaptation points

| Vendor 6.6.98 behavior | Linux 6.18 target | Classification |
|---|---|---|
| `sunxi_iommu_domain_alloc(unsigned type)` returning same global pointer | `.domain_alloc_paging(struct device *)` required on A733 (legacy `.domain_alloc` member guarded by `CONFIG_FSL_PAMU`) | NEEDS_PORT |
| Vendor returns `global_iommu_domain` repeatedly but frees its allocation without clearing global in captured `domain_free()` | Explicit domain ownership/refcount or safe single-domain lifecycle; avoid dangling domain/repeated free | HIGH_RISK_NEEDS_DESIGN |
| Vendor logs `sunxi_iommu_hw_init()` failure and returns domain anyway | Report initialization failure and unwind hardware/page-table/SG resources | HIGH_RISK_NEEDS_PORT |
| `sunxi_iommu_map(domain,iova,paddr,size,prot,gfp)` | `.map_pages(domain,iova,paddr,pgsize,pgcount,prot,gfp,mapped)` | NEEDS_PORT |
| `sunxi_iommu_unmap(domain,iova,size,gather)` | `.unmap_pages(domain,iova,pgsize,pgcount,gather)` | NEEDS_PORT |
| `sunxi_iommu_iotlb_sync_map(...)` returns `void` | Linux 6.18 `int (*iotlb_sync_map)(...)` | NEEDS_PORT |
| Vendor invalidates TLB/PTW and updates gather during unmap | Preserve correct invalidation ordering, boundary alignment and accurate unmapped byte count | NEEDS_TEST |
| Vendor SG scratch and v20 page-table allocation | Retain actual hardware format, verify DMA address widths, alignment, cache sync and full unwind paths | NEEDS_TEST |
| `iommu_device_register(iommu,ops,dev)` | Same three-argument API in exact 6.18 header | ALREADY_PRESENT |

The operator's vendor configuration grep returned **no results**, so there is **no verification of the running stock 6.6.98 `CONFIG_AW_IOMMU_V2` selection** yet. The report does confirm source-level v20 match string and build selection in vendor Kconfig/Makefile. Do not equate those with a proven running config.

### Port gate

First isolate the vendor's effective preprocessor branches, then design domain allocation and shared-controller ownership before writing any wrapper functions. Do not permit any consumer attachment until page-table lifecycle, IOVA ranges and TLB invalidation contracts have passed isolated source and hardware tests. Keep the working Linux 6.18 kernel and DTB unchanged. The vendor DTB's `de0_iommu` master ID 0x08 is an **IOMMU master index**, not a verified complete `iommus` specifier for the display consumer.
